# 振り返り：アルカナフォージ v1.0.0

## 結果
- 企画→プロト→α→β→マスタを完走し、別モデルの最終レビューで「販売可能」の判定を得た
- 実機の自動プレイ40本でクラッシュ0、シミュレータ2,100本で保存の不一致0、p99 2.8ms
- 未達：戦闘時間（約10分。目標15〜25分）、未使用ゴールド（38%。目標30%未満）、人によるテストなし

## うまくいったこと
1. **ロジックと描画の分離、決定的なシミュレーション。** DxLib に依存しないゲーム本体と、画面なしで動くシミュレータを最初に作ったので、バランスを数百本単位で計測でき、保存の往復検査も毎回自動で回せた
2. **ラン進行の Action 化。** UI・シミュレータ・自動操作が同じ Action を送る作りにしたため、自動操作で全画面を巡回でき、スクリーンショットによる回帰と QA がそのまま成立した
3. **別モデルのレビュー。** 自分では見落としていた指摘が毎回あった：ライセンス文書の同梱漏れ、ヒント帯がボタンを隠す、バランス目標の後付け変更、セーブの保存場所、スクリーンショットのキー表記
4. **素材の統一。** Gemini の生成物を CC0 素材のパレットに量子化して縁取るパイプラインで、出所の違う画像の見た目をそろえられた
5. **正直な記録。** 未達を成果書に残し、レビューも「既知の未達」として判断できた

## うまくいかなかったこと
1. **計測のぶれを無視して達成を宣言した。** smart とランダムの差が 10.6pt で「達成」と書いたが、次の計測では 3pt。200本では ±7pt ほど揺れる。宣言の前に信頼区間を計算すべきだった
2. **目標を結果に合わせて書き換えようとした。** 「ふつう」の勝率が下がらないので目標を 30〜45% に広げたところ、レビューで「ゴールポスト移動」と指摘された。正しい対処は設計の変更で、「やさしい」を追加し「ふつう」を当初の目標へ戻したら両立した
3. **見た目の不具合の発見が遅れた。** ボスが白い塊に見える（命中フラッシュが常時点灯）不具合はβ後半まで残った。敵の弱点が画面に一切表示されていないことにも、マスタ直前まで気づかなかった。ボスや敵を追加した時点で、その場面のスクリーンショットを確認していなかった
4. **「プレイヤーに見えているか」の確認がなかった。** 弱点・耐性、マナの意味、合成の操作など、ルールとしては存在するのに画面で伝わらない情報があった
5. **後から作り直した基盤。** セーブを exe と同じフォルダに置き、日本語パスを考えないファイル操作にしていたため、マスタで作り直した。保存場所、クラッシュログ、版表記は最初から入れておくべきだった
6. **設計の深さの問題が残った。** 戦闘中の合成は手札を戻すだけでコストがほぼなく、適当に合成しても強い。そのため、賢い方策とでたらめな方策の差が小さい
7. **環境の罠で時間を失った。**
   - DxLib の多重起動禁止で並列 QA が黙って終了した
   - PowerShell では Math.Max(int, double) が int 版に解決された
   - CRLF の違いで置換が失敗した
   - パスの解釈で Remove-Item がブロックされた
8. **使用上限での中断。** 途中で止まり、「これで完了ですか？」と確認させてしまった。進捗メモは残していたが、中断時の報告で残作業をもっと明確に示すべきだった

## 次に活かすこと
- **数値目標は、本数と信頼区間をセットで判定する。** 差を主張するなら、区間が重ならないことを確認する
- **目標に届かないときは、目標ではなく設計の調整軸を増やす。** 難易度の選択、救済の仕組み、山場の分散など
- **コンテンツを追加したら、その場面のスクリーンショットを必ず見る。** ボス、エリート、反応、新しい画面ごとに
- **「プレイヤーに見えているか」のチェック表をαで作る。** ルールにある情報が、すべて画面のどこかで伝わること
- **プロトの時点で配布の土台を入れる。** 保存先は %APPDATA%、ファイル操作はワイド文字、クラッシュログ、版表記、起動失敗時の案内
- **コア機構には最初から「使う判断」が要るコストを付ける。** 合成なら、クールダウン、素材の消費、マナのいずれか
- **自動操作の表示はプレイヤーと同じにする。** パッド表示ではなくキーボード表示にし、ストア用の撮影に流用できるようにする
- **並列実行の前に、ライブラリの多重起動制限を確認する**
- **人によるテストは計画に入れる。** できない場合は、マスタの冒頭でリスクとして明記する
